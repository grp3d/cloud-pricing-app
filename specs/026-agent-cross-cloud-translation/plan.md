# Implementation Plan: Agent Cross-Cloud Architecture Translation

**Branch**: `026-agent-cross-cloud-translation` | **Date**: 2026-11-19 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/026-agent-cross-cloud-translation/spec.md`

## Summary

The agent translates an AWS architecture to GCP or Azure as a 025 proposal of a new kind,
`translate`. Every service is matched by app data, never by the model:

- **Seed mappings** from 022's standard-architecture rules, generated by the existing resolver
  into a new `service_mappings` table (migration 0013), keyed by a region-independent product key
  each adapter defines (R2–R4);
- **automatic matches** from 024's candidate finder and quality rules, used without asking when
  exact or close (R5);
- **partial matches** used only when the user chooses one in a later message (R7); everything
  else is flagged and left out, and the total is labelled partial.

Two operations, `find_translation` and `propose_translation`, follow the 024/025 pattern: the app
finds and prices, the model chooses by reference (R8); a third, `describe_translation`, re-reads a
translation's figures and caveats for later questions such as "which is cheaper?". The proposal carries a mapping table and a
cost difference summary priced by the engine (R6); accept, reject, undo and redo are 025's
(R1). A translation is stale when its source or the mapping data changes, and must be made again
(R9). The Results pane shows the table and the difference (R11). Prompt 026.1; GC-1 to GC-7 are
eval cases `gc-32` to `gc-38`, live on Claude Haiku 5.5 only (R10).

## Technical Context

**Language/Version**: Python 3.12 (backend); TypeScript 5.6 with React 18.3 (frontend).

**Primary Dependencies**: FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic 2 and DuckDB through
the provider adapters. Frontend: TanStack Query, Radix UI and Tailwind. No new packages.

**Storage**:
- PostgreSQL: new `service_mappings` table (seed mappings) and `agent_proposals.translation`
  column plus the `translate` kind, in migration 0013. Architecture tables unchanged.
- Pricing data: Parquet through DuckDB, read-only and unchanged.

**Testing**:
- pytest unit: product keys per provider (from real catalog rows in the CI fixture), the seed
  generator (pairing, factors, alternatives, omits, byte-identical re-run), the matcher order
  (seed → automatic → partial-only → none), the mapping table and difference summary;
- pytest integration on real Postgres: the seed round trip for all four standard architectures
  to GCP and Azure (SC-006), the operations with the scripted model, partial-pick guard, stale
  refusal, accept/undo/redo/reject leaving the original identical (SC-004), the migration;
- contract: OpenAPI snapshot for the new schemas;
- YAML golden conversations `gc-32`–`gc-38`, scripted by default, live with `-m live_model` on
  Claude Haiku 5.5 only;
- Vitest for the mapping table, the difference summary and the card; one Playwright e2e,
  `agent-translation.spec.ts`, with the scripted provider (translate, accept, undo).

**Target Platform**: the existing Docker Compose stack, and local dev on macOS. No deploy until
the agent features are done (owner).

**Project Type**: web application (`backend/` + `frontend/`).

**Performance Goals**: finding and pricing a translation of a standard architecture in under
10 s on the dev machine (024's searches run 4 at a time; identical searches are made once); a
translation fits 023's round limit (find, propose, answer).

**Constraints**:
- nothing is saved before accept, and the original is never written (FR-005, FR-009);
- every figure comes from the engine (SC-003);
- the CI pricing fixture must cover every seed mapping's SKUs in 022's regions (it already holds
  022's seeded SKUs; the AWS sources come from the AWS seed);
- no live model calls in the default test run.

**Scale/Scope**: a handful of named users; sources of at most 100 items; about 60 seed mapping
rows per target provider.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Check | Status |
|---|---|---|
| I. Pricing Data Integrity | Both sides priced by `calculate_architecture_price`; per-row amounts from those results; differences from unrounded values, over rows priced on both sides; unpriceable and left-out rows named, totals labelled partial; figures reach the model as references only (R6). | Pass |
| II. Data-Layer Separation | Seed mappings are Postgres linking data keyed by product keys, not copied prices (R3). The proposal's `translation` is a record of what was shown, with snapshots; nothing prices from it. Automatic matches aren't stored. | Pass |
| III. Multi-Provider | Product keys and key lookup are per-adapter functions behind the shared contract (R2). The translation code is direction-neutral; only the offered directions are limited (FR-011), by data, not by code branches. | Pass |
| IV. Type-Safe Contract | `TranslationOut`, `MappingRowOut`, `CostDifferenceOut` are Pydantic models; generated TS types are regenerated (contracts/agent-api.md). | Pass |
| V. Test-First | Tests first for product keys, the generator, matching order, the summary, the round trip, the operations, the guard, the stale check and the migration. Golden conversations GC-1 to GC-7 are eval cases; scripted model only by default. | Pass |
| VI. Simplicity | No new packages, routes or pages; 024's matcher and 025's proposals reused; one table, one column. No Admin review queue (clarification 3); automatic matches not cached. | Pass |
| VII. Agent acts as the user | Sources are architectures the user can open; the result is their own private architecture; nothing saved before accept; one undo. The model picks by reference; a partial match needs the user's turn (R7). Architecture text stays data. Every step is in the activity log with mapping version and snapshots. | Pass |
| VIII. Models, cost, secrets | No model-specific code; fits the round limit; accept/reject/undo/redo make no model call. Live evaluation on Claude Haiku 5.5 only, under the paid-usage rules. | Pass |

**Post-design re-check (after Phase 1)**: unchanged, all pass. Points to watch:
- GCP product keys strip location words by a reviewed pattern list; a test must show every seed
  key resolves in each of 022's regions to 022's SKU, or the key definition is wrong;
- the partial-pick guard reads the activity log; its summary format becomes part of the contract
  and needs a test;
- checking only Haiku: as 025, other models' results are reported, not required (SC-005).
